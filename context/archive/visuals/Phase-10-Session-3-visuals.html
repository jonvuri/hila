Phase 10 · Session 3 — Plugin view composition model

Session 2 fixed the frame: plugins contribute face types and commands; the shell — stream + launcher + system edge — is fixed core infrastructure. This session pins the contract underneath: what a face type declares, what hosts provide, how a subject resolves which face renders it, and where configuration lives. Companion to context/Phase-10.md §3.

Givens, not reopened: no plugin top-level views · substrate is the guaranteed floor · v1 fidelity is substrate-first (9.7); composed faces are this phase's sugar · nodes source children via loose / container / view · grid is coalescing, not a paradigm.
Round 1 → 2: D1 (query/recipe split) and D3 rung-1 deferral accepted; the recursion-through-hosts direction agreed · D4 reopened — the regioned-host proposal flagged as potentially deciding layout ahead of proven need; §4 now carries the full option space with tradeoffs and a revised recommendation.

0 · The one-sentence model

Hosts own chrome and recursion; faces own interiors; subjects own their data; a fixed ladder decides which face renders which subject. Every box below is one of those four words.

1 · D1 — The face config splits: queries belong to subjects, recipes to rendering

Today's FaceConfig bundles a query with the rendering choices. Under 9.7 the data source is already the subject's own business — a container node is its extent, a view node is its query, the mesh is the mesh. Proposal: the face config sheds its query and becomes a pure rendering recipe — { faceTypeId, slotBindings, settings } — attachable to any subject whose row shape it can bind. The slot-resolution chain (explicit → name → type+position → fallback) is unchanged and is what makes recipes portable.

Why it matters: the §3b launcher continuum (transient search ↔ persisted ≔ view) only carries the query across; recipes attach to either end without duplication. Sort/filter live with whichever plane they modify: a view's ORDER BY/WHERE is subject (data); a grid's column widths or a kanban's lane column is recipe (rendering). The sugar-level sort/filter gestures (§3b's shared authoring layer) compile into the subject's query, not into the recipe.

2 · D2 — Chrome is host-owned, interiors are face-owned; hosts do the recursion

The host-context contract in one split: everything that says where you are and how to move is drawn by the host, identically for every face; everything inside is the face's. And composition is recursive only through hosts: when a face's interior contains another subject (a container block inside a panel's children region), the face yields a row slot back to the host, which runs the ladder again. Faces never instantiate faces.

Sizing follows the same split: hosts always own width (panel column width; row slot width) and hand the face a density tier, not pixels. In row context the host also owns the height budget of an expanded block region (windowing/paging past it — the 9.7b deep-mirror machinery), with exact budgets a §4 token-pass detail. Drill-in is chrome too: clicking a block's frame focuses the node (boundary hop); clicking inside it is the face's interaction.

3 · D3 — Face affinity is a ladder; the preferred face lives on the subject resolves Plan.md #5

Which face renders a given subject? A fixed three-rung ladder, run by the host at every slot. The preferred face is a fact on the subject node — equivalently, on the matrix, via its 1-to-1 owner — set by the plugin at creation (declarative manifest) or by the user through panel/block chrome. It rides the membership plane: "tasks render as a grid" follows the Tasks container everywhere it appears. Per-appearance overrides (rung 1) are modeled but deferred: nothing in v1 stores them, and the ladder leaves room without them.

The recipe's face type carries both context renderings, so one preferred recipe answers both "as a block" and "as a panel" — no per-context affinity slot. If a face type lacks one context's rendering, that context falls to rung 3 (the floor), never to a different recipe. Plan.md open question #5 closes: the preferred face is a subject-level recipe; the substrate remains the universal fallback.

4 · D4 — Interior ownership: the option space round-2 deep dive

Round 1 proposed a regioned host; the flag against it is real — a region framework minted ahead of any second consumer, freezing layout decisions early. The deep dive splits the question in two. First, the invariants: four guarantees every option needs, small, and the part that genuinely must be decided this session. Second, layout ownership — the actual open axis — where a survey of every contemplated face collapses the scope considerably.

4.1 · The invariants (option-independent — the real contract)

I1 · recursion

Faces never mount faces

A face's interior containing another subject yields a slot back to the host, which re-runs the ladder. Composition depth belongs to hosts; the ladder stays the single authority.

I2 · reachability

Every hydrated column stays reachable

Whatever a face doesn't consume, the host guarantees access to (a disclosure affordance, at minimum). Reachability is a contract term, not face discipline.

I3 · chrome

Chrome is host-owned

Frames, container borders, drill-in, breadcrumbs, focus headers — identical for every face. Clicking chrome navigates; clicking inside is the face's interaction.

I4 · x-ray

X-ray snaps to substrate

The global toggle renders the substrate structure regardless of what any face does — the conformance escape hatch is unconditional.

4.4 · Recommendation: F now, D as the growth path, A never frozen, B never

A face type declares up to two renderings — line and collection — and hosts map presentation to them. The panel scaffold (identity · fields · collection region(s) · relations) is not part of the plugin contract at all: it is shell-owned substrate structure, free to evolve in the §4 token pass without breaking any plugin. Session 2's "row and panel host contexts" refines rather than changes: row/panel are host presentations; line/collection are what faces supply.

Why this and not the others: vs A — no region-substitution framework is minted, and the scaffold's arrangement stays a design decision instead of an API; vs B — I2 stays by-construction instead of becoming face discipline, and no face pays whole-interior cost; vs C alone — kanban/calendar get a home (collection renderings) instead of stretching a styling vocabulary; vs D now — D is exactly what to extract when the first real whole-interior face appears, from real consumers, the same way the plugin API itself was extracted ("once patterns were clear from multiple real consumers"). F is forward-compatible with D: line/collection renderings become two of D's parts unchanged. The current overflowBehavior enum still dissolves (unbound columns land in the scaffold's fields part). The check for this round: does the line/collection scope reduction hold for you, or do you see a near-term face that genuinely needs to own panel layout?

For every contemplated face, A and F render identical pixels — a kanban children-region substitution (A) and a kanban collection rendering (F) look the same on screen. The difference is the promised surface: A promises plugins the panel; F promises them two renderings. Promises are what you can't take back.

5 · D5 — Density and fidelity are view state, never stored in recipes

The substrate renderer is already keyed (row, columns, density, fidelity). The contract generalizes that key to every face: density is a small ordered tier computed by the host from available width (never raw pixels, never persisted); fidelity (composed ↔ substrate) cascades down scopes — shell → panel → block — with the global x-ray toggle living in shell state (session 2) and finer overrides as ephemeral view state. Recipes stay pure rendering preferences; what you'd get on any given screen is always reconstructible.

6 · D6 — One command registry, two exposure surfaces

The other half of the contribution surface. Plugins register commands into one registry; each declares where it surfaces — the / menu (make), the ⌘K launcher (act), or both — plus what subject context it needs. The existing slash-commands.ts shape (id · label · keywords · run) is the seed; it gains a surfaces field and moves from a hardcoded array to the registry. Launcher-side ranking/UX is §3b's business; only the registration shape is fixed here. 

type Command = {
  id: 'hila.tags.promote'            // namespaced by plugin
  label, keywords                      // as today
  surfaces: ('slash' | 'launcher')[]  // where it appears
  context: 'node' | 'none'            // needs a subject? (slash always has one;
                                       //  launcher passes the provenance node)
  run(subject?, …)                     // delegates to ops, as today
}

The provenance rule from session 2 carries over for free: a launcher command that creates something homes it under the node focused when ⌘K was invoked — the same subject parameter, supplied by the shell.
