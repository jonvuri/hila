0 · Session inputs — three calls made before round 1

Three inputs were put to the user ahead of this round because each shapes several determinations at once. They are recorded as inputs (I1–I3), not determinations — but they are load-bearing below.

I1 · ⌘K ownership

The launcher owns ⌘K everywhere

Including inside the ProseMirror editors, where Mod-k currently means insert-link (src/editor/keymap.ts). One key, one meaning, in every context. Insert-link relocates — and D28 proposes the launcher itself absorbs the job (⌘K → find → ⌘⏎ inserts a ref), recovering the muscle memory rather than just displacing it.

I2 · The statelessness line

In-memory session recency is allowed

"Stateless v1" means no new persisted stores — not amnesia. The launcher may read current stream state (what's on screen) and this-session focus history; all of it resets on reload. Deferred frecency becomes "persist what already exists," not a redesign.

I3 · Feel calibration

Raycast/Linear density × Obsidian's two tempos

Dense sectioned results with inline secondary actions, and a thin known-item switcher as the default tempo that escalates into a fuller query surface. Spotlight-minimalism and VS Code's hard mode-split were not selected. This maps directly onto the phase doc's "one surface, two tempos."

What the launcher is assembled from

Nothing in this session mints new model. The launcher is a shell surface composed from four settled parts — this session decides only how they are arranged, ranked, and keyed:

1 · D20 — Placement & anatomy proposed

Where does the surface physically live when ⌘K fires?

A — Centered floating palette over a dimmed stream recommended

＋ Matches the doctrine exactly: a gesture that is never a place — it floats above all places, acts, and vanishes. The stream stays visible (dimmed) underneath, which keeps the provenance node — the launcher's subject — literally in view.

＋ Geometry is free to grow downward through the tempos (D25) without reflowing any place.

− Yet another overlay; the §4 token pass must give overlays a single consistent treatment (launcher, slash menu, system edge).

B — Top-docked bar that pushes the stream down

＋ Browser-omnibox familiarity; never covers content.

− Docked chrome reads as a place — a persistent region of the shell — exactly what session 2 retired tabs for. Reflows the stream on every open. Growth through tempos would keep pushing content around.

C — Anchored to the focused panel's header

＋ Visually pins the gesture to its provenance subject.

− The launcher's action is global ("go anywhere"); anchoring it to local geometry misstates its scope, breaks when no panel is focused, and couples a shell gesture to panel chrome that §4 hasn't settled.

D20 (proposed): centered overlay palette, stream dimmed beneath.

Fixed width (~640px at standard density), top-third vertical placement, grows downward only. Opening never disturbs the stream; dismissal restores exactly what was there. The overlay treatment itself (scrim, elevation, radius) is a §4 token placeholder — settled here is only the relationship: floats above places, anchored to none.

Amended (close): the fixed width is the quick tempo's. Deep tempo expands to a viewport-proportional frame — still floating, clear margin on all sides, never full-bleed — to show as many preview rows as comfortably fit. Proportions ride the §4 pass. See §18.

2 · D21 — Result layout & sectioning proposed

One input matches two different things at once (3b-i D15): object names across families (nodes, containers, views, types, matrixes — and commands), and — as the uncommitted-text residue — row content via the compiled spec (label-role LIKE, kind: everything). How do those results share one list?

Superseded (round 2): option A chosen — the family sections are retired for a flat unified list; active family-narrowing replaces passive sectioning. See §14 (D21 revised · D31). The row anatomy (line renderings + ancestry breadcrumbs) and the hoisting/top-hit reasoning below remain the record of why sections were considered.

A — One flat, unified ranked list

＋ Maximum relevance density; no wasted headers.

− Family placement jitters per keystroke, so ⏎ becomes a gamble — the top item's kind is unpredictable. Spotlight lives with this; a keyboard-first tool shouldn't.

B — Fixed family sections, fixed order, no top slot

＋ Perfect spatial memory: places always live where places live.

− An exact-name command or view match gets buried beneath weaker place matches purely by section order; the best answer isn't first.

C — A small unified top-hits band, then fixed family sections recommended

＋ The Raycast/Linear shape (input I3): the top band (≤3) is earned purely by match quality across all families, so ⏎ on the best match stays one keystroke; the sections beneath keep spatial memory for scanning.

− An item appears "twice" conceptually (top hit + its family); resolved by hoisting — a top-hit item is removed from its section, not duplicated.

D21 (proposed): hybrid — top hits (≤3, hoisted) over fixed family sections.

Section order: Top hits · Places · Commands · Content. Places is every name-matched object in the forest — containers, views, docs, type-nodes, matrixes (a matrix and its subject node are 1-to-1; one entry). Content is the residue text run through the compiled spec (rows whose label matches). Sections cap at 5 with a trailing "n more…" row that expands in place; sigils (D22) narrow to a single family, uncapped. Every result row is the object's line rendering as it appears app-wide (D14) plus a right-aligned ancestry breadcrumb resolved down the session-2 ladder (provenance → home → membership).

4 · D23 — Matching & ranking, stateless v1 proposed

Two sub-decisions: what counts as a name match, and how ties order.

The matcher

A — Prefix · word-prefix · substring, no fuzzy recommended

＋ Predictable, explainable, and — decisively — congruent with the residue: the same typed text simultaneously runs as a LIKE over row content (3b-i D2). If names matched fuzzily while content matched by substring, one input would obey two matching physics at once.

− No "rdmp" → "Roadmap" tricks. Acceptable: typo tolerance is an FTS-era question, and the spec already insulates that migration.

B — Fuzzy subsequence (VS Code style)

＋ Forgiving of sloppy typing.

− Ranking becomes score-soup (why did that win?); incongruent with the LIKE residue; and the failure mode — confidently wrong matches — is worse than the miss it prevents. Rejected for v1.

The signal stack

Every signal below is computable from content, current stream state, or session memory (I2) — nothing persisted. Higher tiers strictly dominate lower ones; lower tiers only break ties.

1Match tier

exact name > name prefix > word prefix > substring. The only signal that can earn the top-hits band.

2Family prior

places ≥ commands > content rows — a mild thumb on the scale between equal match tiers, not a veto.

3On-screen boost

the object is in the current stream (an open panel, a visible block). Derived from stream state — the launcher's "you probably mean the thing you're looking at."

4Session recency

focused earlier this session (in-memory, resets on reload — input I2). Becomes frecency later by persisting, without reordering this stack.

5Structural tiebreaks

shallower home depth, then shorter label, then rank order. Deterministic — the list never shuffles between identical inputs.

D23 (proposed): word-boundary matching, five-tier dominance stack, deterministic.

Determinism is the point: the same input always yields the same list within a session. Frecency (deferred) slots in as tier 4's persistence, changing no other tier — the designed growth, mirroring how FTS swaps into the text compile rule.

＋ Purest; zero risk of home-surface creep.

− Wastes the frame's most common moment. "Jump back to the thing from five minutes ago" is the single highest-value launcher act, and it requires zero typing to serve.

6 · D25 — The quick↔deep continuum the crux

The phase doc calls it "one surface, two tempos." 3b-i settled what both tempos edit (the spec) and how deep escalates out (save-as-node). Remaining: how does the thin switcher become the query workbench — a growth, a mode, or an exit?

A — Continuous growth: tempo is a fact about the spec recommended

＋ Mirrors the settled escalation-tier principle exactly — "a block's mode is a fact about its SQL, recomputed on read" becomes "the launcher's tempo is a fact about its spec." Text-only spec = quick tempo (sectioned go-list, D21). The moment any non-text dimension commits — a chip exists — the surface is in deep tempo: chip row visible, results become a single filtered preview (D26), result count and save affordance appear. No toggle, no mode state to desync; deleting the last chip is returning to quick tempo.

− The launcher can now be a big surface; the doctrine risk is it starting to feel like a place. Contained by a hard ceiling (below).

B — An explicit mode toggle (a key flips quick ↔ query layout)

− Mints a second state that merely shadows what the spec already says — chips would exist while the surface claims quick mode, or vice versa. "Chips are the state" (D14) forbids exactly this. Rejected.

C — Escalate by leaving: first chip materializes an ephemeral view panel

＋ Doctrine-flattering on the surface: dwelling belongs in places, so make depth a place immediately.

− Reopens a settled determination: Query-Spec.md's surfaces table gives the launcher a transient in-memory spec with chips — this option deletes that tempo. And "ephemeral" nodes aren't ephemeral here: placeless creation homes by provenance, so abandoned escalations would litter real positions in the forest, or demand a new throwaway-node mechanism. Rejected.

D25 (proposed): continuous growth; tempo derived from spec shape; a hard ceiling before place-ness.

The ceiling: the deep launcher shows a read-only preview — line renderings plus spec-touched value columns (D26), windowed, with ⏎ still meaning go to this row. It never mounts a face, never edits a cell, never offers add-row (the view firewall applies even to a preview of a query). Anything past the ceiling — editing results, a real grid, a recipe — is exactly one gesture away: save-as-node (D30) turns the spec into a place and focuses it. The launcher remains a gesture at every tempo; depth changes what it shows, never what it is.

7 · D26 — The deep-tempo preview: the spec projects it proposed

The spec permanently has no projection dimension (3b-i D2 — compiled SQL is always SELECT d.*). But the preview must choose columns to show. Whose choice is it?

A — Label-only list, always

＋ Simplest; quick and deep tempo look identical.

− Filtering on due and not seeing due dates makes the preview useless for exactly the verification the deep tempo exists for.

B — Spec-touched columns project the preview recommended

＋ One derived rule, no state: show the label role, plus every column referenced by a committed where/order chip, in chip order, capped by width. The columns you committed to are the columns you see — the preview explains the result set by construction.

＋ Doctrinally clean: this is a rendering choice by the surface (a host concern, like fetch-narrowing — D2's carve-out), not a projection in the spec. Nothing round-trips through SQL; a saved node's face recipe owns real column visibility later.

− Opaque-leaf chips reference no recognizable column — they project nothing (honest: their content cannot speak, same as their labels).

C — Full substrate grid in the launcher

− Crosses D25's ceiling: mounting the substrate collection rendering makes the launcher a host with recursion obligations (session 3's ladder), i.e. a place. The grid is one save away. Rejected.

D26 (proposed): preview = line rendering + spec-touched columns, chip-ordered, width-capped, read-only.

9 · D28 — The secondary act: ⌘⏎ proposed

Raycast/Linear density (I3) wants one inline secondary action. Which one earns the slot in v1?

A — Insert a ref at the invoking cursor recommended

＋ Closes the loop I1 opened: ⌘K stole insert-link from the editors, and this gives the job back better — find anything (with chips, scopes, the whole grammar), ⌘⏎, and an inline ref lands where your cursor was. The launcher's find machinery becomes the link dialog.

＋ Perfectly scoped availability: enabled only when invoked from an editor with a cursor (the invocation context the launcher already captures for provenance); disabled with a stated reason otherwise — the settled honesty rule.

− Meaningless for command rows (ignored there).

B — Peek: preview the object without dismissing

＋ Nice for verification.

− A preview pane is real new surface (sizing, fidelity — §3 contract questions) for a v1 whose deep tempo already previews rows. Defer.

C — Open as a block under the provenance node

− That's a make gesture — structural insertion is the / surface's jurisdiction (session 2: ⌘K goes, / makes). Crossing the two gestures' jurisdictions for a shortcut muddies the cleanest line the model has. Rejected.

D28 (proposed): ⌘⏎ = insert ref at the invoking cursor; editor-context only; commands ignore it.

14 · Round 2 — quick family-narrowing the round-2 crux

The D21 call: flat unified list — family sections retired. The insight behind the call: sections answered passively ("here are your matches, grouped") a question the user wants to answer actively ("I mean a type"). And the passive answer was redundant — every result row already carries its family on its face, because rows are the objects' app-wide line renderings with their settled glyphs ([] ≔ # ›). Sectioning duplicated the glyph channel and taxed the common case (scanning one ranked list) to serve the rarer one (family-directed search). So: flat list for reading; a deliberate, fast gesture for narrowing. This section decides that gesture.

The clarified search scope, first

Recorded as a scope revision to D23: the launcher searches all named objects (nodes of every stripe — docs, containers, views, type-nodes, matrixes — plus commands) and all label-role and content-role columns. Names and labels strictly outrank content. In the flat list this replaces D21's sections and D23's family-prior tier with two relevance bands:

ANames & labels

an object's name / a row's label-role match. Within the band: match tier → on-screen boost → session recency → structural tiebreaks (D23's stack, minus the dissolved family prior — merit only, no caps).

BContent

content-role column matches, rendered as snippet quotes. Always below band A; same internal ordering. The band boundary is invisible chrome — no header, no divider; the snippet form and glyphs signal it.

Amended (close): the A/B split is softened from strict bands to a default weight — names & labels outweigh content, but a significantly more relevant content match may outrank. One blended, deterministic ordering; coefficients are implementation-time tuning, not design. See §18.

The options

N-A — Sigil filter tokens: the sigil is the hotkey recommended

＋ A sigil typed at the start of the input is already a single unmodified keystroke — the fastest physically possible gesture, needing no new binding. What round 2 adds is reification: the sigil renders as a visible filter token (dotted, hollow — visually a different species from spec chips), the rest of the typing matches within the family, ⌫ at the start deletes it.

＋ Surface channel, not spec channel — the honesty line: a filter token narrows what the finder shows; it never compiles, never saves, never appears in a saved node. (Committing an object out of the narrowed family via ⇥ consumes the token into the resulting chip — the sigil is also the fast on-ramp into chip authoring, the "quicker than typing out a whole chip" path.)

＋ Sigil-alone = family browse, replacing the rejected lens furniture with a gesture.

− Discoverability — sigils must be learned. Answered by N-B, which is complementary rather than competing.

N-B — Families as findable objects (the discoverability half) recommended, with N-A

＋ D15's doctrine is "names are the only grammar" — so let families have names. Typing types surfaces a suggestion row for the family itself: "# types — narrow to types"; ⇥ applies the filter token. The row displays its sigil, so the menu path teaches the fluent path — precisely the D16 mastery-ladder shape (menu → typeahead → sigil), extended from ops to families. No memorization required to start; one session of use to graduate.

＋ Pointer garnish for free: every result row already renders its family glyph — clicking the glyph applies that family's filter token ("more like this"). Zero new furniture.

N-C — A filter strip with counts (segmented control under the input)

＋ Gives the "scent" sections used to give (All · Places 4 · Types 1 · Commands 2 · Rows 11) and a pointer path; Linear does this well.

− It's standing furniture in a gesture surface — paid on every open, used rarely (the calibration above). And its keyboard story lands back on digit-hotkeys (N-D's problem) or a cycle key the map doesn't have spare. Not v1; if scent proves wanted, a match-count can ride the filter token itself ("# types · 12") without minting the strip.

N-D — Global hotkeys (⌘2 → @, ⌘3 → #; insert the token, or open pre-narrowed)

＋ The open-pre-narrowed behavior is genuinely nice ergonomics for a hot workflow.

− ⌘-digit is the browser's tab-switching range. Chrome/Safari treat ⌘1–9 as browser-level shortcuts; while hila lives in the browser these are at minimum contested and likely not interceptable at all — a dead-on-arrival home for a core gesture (a desktop shell later could revisit).

− Matches the user's own skepticism: family-narrowing is a secondary flow (the use-case table), and global keys are the scarcest resource in the map. Inside the launcher, N-A already is a single-keystroke hotkey — a modifier chord would be slower than the sigil it triggers. Deferred entirely; if ever revived, it is additive (a binding that types the sigil), changing nothing designed here.

15 · The empty state, revised — recovery and guidance proposed

D24's jump-back list held; the lens tail didn't — and shouldn't have: §14 makes browsing a gesture (#, [ alone), so the tail was furniture duplicating a keystroke. Its two replacements both serve the empty frame's real jobs: recovery and guidance.

Recent deep searches — the recovery point

A spec with committed chips is real authored work; Esc discarding it instantly (the accepted D27 call) is only safe if discard is cheap to undo. So: when the launcher is dismissed with ≥1 chip committed, the spec is pushed onto an in-memory recent deep searches list (cap 5, identical specs deduped, session-only — squarely inside I2). ⏎ on one restores the spec into the launcher — chips, text, deep tempo, exactly as dismissed — it does not execute and jump. Restore-don't-run keeps it a recovery mechanism, not a bookmark system: the durable form of a search worth keeping is save-as-node, and its default name (D30) even matches what these rows display. The Esc call and this list are one design: instant dismissal because recoverable.

The help footer and the ? guide

A — Static footer line + ? expands to the full guide recommended

＋ One quiet line of the load-bearing gestures, always in the same place (spatial memory applies to help too), with ? — on empty input only, where it can't collide with typing — opening a one-screen keyboard guide: the launcher's map (D27) plus the app-wide gestures (/ make, focus keys, editor basics). Sourced from the command/shortcut registries wherever possible so the guide cannot drift from the bindings.

B — Rotating hints

− Unpredictable content in a predictable frame; the hint you need is never the one showing, and it reads as noise once learned. Rejected.

D24 (revised): empty state = jump back (≤6) · recent deep searches (≤5, restore-not-run) · static help footer. No lenses, no directory.

16 · Save-as-node is always live correction

Round 1 gated ⌘S behind deep tempo ("nothing committed to save"). User review asked why — and the answer is the gate was simply wrong: it contradicted a determination this session inherits. 3b-i settled that kind: everything — the zero-chip cross-matrix union — saves fine, flagged read-only, with the pick-a-kind nudge (Query-Spec.md). A text-only quick-tempo search is that spec, with a text residue. There is nothing else it could clash with: the spec is always compilable (text-only compiles to the union + label LIKE), homing by provenance doesn't care what the spec contains, and the read-only firewall already handles the editability question.

D27/D30 (revised): ⌘S is live whenever the spec is non-empty — any text or any chip. Only the truly empty spec disables it (with the stated reason: nothing to save).

Quick-tempo save compiles the residue as-is: kind: everything + text → a read-only view node named by the same default-name rule ("everything · “road”"), with the pick-a-kind nudge in the save bar. Tempo remains purely a rendering fact (D25) — it never gates a capability. The keyboard-map table's ⌘S row is amended accordingly (noted at §8).

18 · Round 3 — final calls, and close

Every open item resolved on user review; no round-4 questions remained. The calls:

  • D21/D23 refined — weights, not bands. The name/label-vs-content split is a default relevance weight in one blended ordering, not a hard two-band separation: a significantly more relevant content match may outrank a weak name match. The settled structure is: one flat list · blended deterministic ranking · the signal set (match quality, match target, on-screen, session recency, structural tiebreaks). Coefficients are expected implementation-time tuning — deliberately not designed here.
  • D31 + D32 accepted. N-A and N-B together — the sigil/name pairing for families deliberately rhymes with how chip ops pair glyphs with prose names (D16). No view sigil until proven need; views read fine as nodes.
  • Save binding: ⌘S (the ⌘⇧⏎ alternative retired).
  • Caps: jump-back 6 · recent deep searches 6 · quick-tempo results 12 (expandable). Deep tempo expands to a viewport-proportional frame (margin on all sides — floating, never full-bleed, never a place), showing as many preview rows as comfortably fit; amends D20.
  • Live-relative date tokens — designed growth, homed in Query-Spec.md. Obviously wanted (task lists, "today" views). The audit for a second runtime-parameter consumer to drive a generalization found none in the immediate plan: host-bound execution params (:window_start, :collapsed_keys) are a different, already-general layer, and Phase 11's date('now') column defaults evaluate at write time (no invalidation need). So the shape is recorded — compile to a reserved :today-family runtime parameter, recognizer lifts it back, executor binds an environment, invalidation gains a clock (re-run at rollover) — and the build waits for a second member of the environment family (:me identity, :here context) or proven need. v1 freezes relative tokens to literals with the save nudge (D29).
