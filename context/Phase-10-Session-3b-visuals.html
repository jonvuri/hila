0 · The one-sentence model

Gestures edit a spec; the spec compiles to canonical SQL; SQL is what is stored and run; a recognizer lifts stored SQL back into the spec. The spec is a view over SQL — never a second source of truth.

This inverts Metabase's arrangement (structured spec canonical, SQL an irreversible escape hatch) and instead generalizes a pattern hila already ships: recognize-updatable.ts lifts write-back structure out of stored SQL today, and §9.3 already rewrote the subtree snippet so its emitted SQL qualifies. The spec is recomputed from SQL on read, like updatability — there is no conversion moment, hence no one-way door inside the dialect. The door only exists at the dialect's edge, and it's marked.

2 · The frame: one spec, three surfaces

The same spec state drives three surfaces at three tempos. Design the vocabulary once; each surface chooses which gestures it exposes and how.

3 · D1 — What is canonical? the crux

Everything else keys off this. Four defensible arrangements:

A · Spec-canonical (the Metabase arrangement)

Store a structured spec on the view node; compile to SQL at run time. Raw-SQL blocks are a separate “native” kind.

＋ Gestures always work on saved views; no recognizer needed; spec can evolve compile targets freely (LIKE→FTS invisibly).

－ Contradicts §9.3's settled executed == stored; splits view nodes into two kinds; recreates Metabase's one-way door the moment anyone needs raw SQL; agents must write spec JSON instead of the SQL they're fluent in; x-ray shows a derived artifact, not the truth.

B · SQL-canonical + dialect recognizer recommended

Gestures emit SQL in one deterministic dialect (the compiler's only output shape). The recognizer — a sibling of recognize-updatable — lifts dialect SQL back into a spec whenever a gesture surface mounts. Hand-edited SQL that stays in the dialect keeps its chips; SQL outside it degrades to a “custom SQL” chip.

＋ One storage story (SQL, executed == stored) — consistent with §9.3, sync, x-ray, and the MCP write path; the recognizer pattern is already in production; no conversion moment, so no cliff inside the dialect; agents writing plain dialect SQL get chips for free.

－ The recognizer must grow in lockstep with every new gesture (compiler and recognizer are a matched pair — a conformance test suite keeps them honest); recognition is binary, so a stray hand edit can drop a block from chips to raw (mitigated in §6).

C · Dual storage (spec + SQL sidecar)

Store both; spec authoritative until the user edits SQL, then flag the spec stale.

－ Two sources of truth with a divergence bit — precisely what §9.3's executed == stored exists to prevent. Rejected unless B's recognizer proves intractable.

D · Structured tree with SQL leaves, stored (the Obsidian Bases arrangement)

Store an and/or/not tree whose leaves are SQL fragments; assemble at run time.

＋ Trivial round-trip (storage is the spec) while keeping raw power at the leaves.

－ Still spec-canonical storage: executed SQL becomes derived, a new format is minted, and full-query power (a hand-written join) needs a degenerate one-leaf tree. The leaf idea itself is worth keeping — inside B, as a raw-fragment predicate chip (§4) — without storing the tree.

Proposed determination D1

B. SQL stays the only stored, executed form (§9.3 unbroken). The spec is a derived, in-memory view over SQL, lifted by a recognizer that is sound on exactly the compiler's output dialect. The compiler and recognizer live together in src/sql/ beside recognize-updatable.ts, with a round-trip conformance suite (recognize(compile(spec)) ≡ spec for all specs; property-tested).

4 · D2 — The spec's dimensions (v1 cut)

Six dimensions. Each is one gesture, one chip color, one compile rule — and each compiles into the same single-base-table shape the write-back recognizer already accepts.

Sub-question D2a — kind: everything and the union problem

The launcher's zero-chip state searches labels across all matrixes + matrix titles — a cross-matrix union. That shape is fine transiently, but it is not single-base-table, so a saved union view would be read-only and chip-less. Options: (i) allow saving it as a raw (recognizer-rejected) block — honest but a dead end; (ii) recommended the save gesture nudges: “pick a type/container to save an editable view” — union saves allowed but flagged read-only; (iii) forbid saving unions. (ii) keeps the escalation smooth without pretending unions are editable.

6 · D4 — Escalation and the honest cliff

Recognition is recomputed, never stored — so the “mode” of a block is a fact about its SQL, not a sticky state. Three tiers, all visible:

tierwhensurface showsyou can
chips default SQL is in the dialect (all compiler output; friendly hand/agent edits) full chip row; “view SQL ▸” collapsed edit any dimension by gesture; open the SQL anytime — closing it re-recognizes
chips + leaf dialect shape, plus WHERE terms the recognizer can't type as predicates normal chips + a ƒ fragment chip per opaque term keep using every other gesture; the leaf opens as a one-line SQL editor (the Bases idea)
custom SQL outside the dialect (joins, aggregates, unions, hand-restructured) a single custom SQL chip + the query text edit SQL directly; updatability still applies independently (recognize-updatable is a separate, narrower lift)

The middle tier is the load-bearing one: it means a single exotic condition doesn't evict the whole block from gesture-land. That containment is what makes binary-per-term recognition feel safe, where Metabase's binary-per-query conversion feels like a trapdoor. And the rule no silent rewriting carries over from §9.3: gestures never reformat SQL the user hand-wrote unless a gesture is actually used — the first chip edit on a leaf-bearing block recompiles only the terms the recognizer owns, preserving opaque leaves verbatim.

7 · D5 — Write-back by construction

The compiler's output shape is chosen to be exactly what the existing machinery already trusts:

  • Single base table + d.* + id always — every compiled view passes recognize-updatable, so hydrated cells are editable with no “+ id to edit” affordance ever needed on gesture-built views. That affordance remains only for hand-written SQL.
  • Subtree scope via single-table EXISTS — the §9.3 rewrite already proved this form keeps updatability recognition sound.
  • Insert stays anchoring-governed (the view firewall, 9.7): no compiled view gains an add-row affordance from being gesture-built — the host still omits it for view subjects. Gestures change what you see, never what owns.
  • Parseable by the invalidation engine — compiler output is plain SELECT, so the tables-visited AST machinery and prepared-statement reuse apply unchanged; text/value chips compile to bound parameters, so launcher keystrokes re-bind rather than re-prepare.

10a · Why the design holds — three structural properties, not a small subset

  • Growth is per-clause, so complexity is additive, not multiplicative. The recognizer never has to understand SQL — only the shapes the compiler can emit, clause by clause, plus balanced-blob leaves everywhere else. Each row in the table above touches one clause position; none reopens the others. recognize(compile(spec)) ≡ spec stays property-testable per clause.
  • The flat chip row mirrors SQL's own spine. A SELECT statement is a flat clause list (FROM · WHERE · GROUP BY · ORDER BY · LIMIT); SQL's hierarchy lives inside clauses (subqueries, boolean trees) — exactly where leaves and the one compound-chip primitive go. Flatness isn't a UI simplification fighting the medium; it's the medium's own shape. MBQL is the long-run evidence: a flat clause map carried a decade of BI usage, and its pain concentrated precisely in joins-for-columns and expression trees — the two places this design routes to tier 3.
  • Hierarchy pressure and write-back loss concentrate in the same features — and the view layer already owns those needs. Column-widening joins, general unions, projection: each would both break the flat row and kill editability. But showing an aspect's fields beside its host is the scaffold/fields region's job; choosing visible columns is the recipe's; heterogeneous browse is the launcher's. The pressure is diverted architecturally, not deferred and accruing.

The honest residue: correlated conditions across paths (“tasks whose due date is past their project's deadline”), N-way column joins, arbitrary trees — leaf or tier-3 territory permanently. A projectional editor could grow without that ceiling; the price would be spec-canonical storage and every cost D1 rejected. The ceiling is the deal.

Net new UI machinery across the whole growth path: one primitive — the compound chip (a chip containing a flat chip list), shared by OR-groups and traversal inner-predicates, capped at one level.

11 · The leaf taxonomy — and the CTE source chip round-2 proposal

Round 1 minted one escape hatch: the fragment leaf, in WHERE position. The general rule it was an instance of: every clause position gets either a canonical chip grammar or an opaque leaf. The proposed CTE chip is the FROM-position leaf — and it's the strongest of the three.

positionleafholdsthe chips around it
WHERE ƒ fragment one opaque boolean term all other dimensions keep working (round 1, §6)
FROM WITH source a full opaque SELECT, as a CTE the outer query reads from scope · text · predicates · order · limit all operate on its output
SELECT ƒ computed one opaque expression column (dry) untouched; the extra column just appears (later, cheap)

The source chip opens into the SQL editor scoped to the CTE body. Cells are dry here (opaque body) — no pretense of editability.

Why it's sound, mechanically:

  • Recognition stays cheap. The lift needs: a WITH name AS (balanced-blob) prefix + a dialect-shaped outer query whose FROM is the CTE name. The body is never parsed by the recognizer — the existing AST machinery (tables-visited invalidation, sandbox authorization) already walks full statements including CTEs, so those layers are untouched.
  • Column vocabulary by introspection, already precedented. The chip editors need the CTE's output columns for predicate/order pickers; QueryBand already synthesizes columns from result keys today. Chips that need columns the output lacks (scope needs position identity; text needs a label-role column) disable with a stated reason rather than guessing.
  • Write-back composes recursively. recognize-updatable rejects WITH today as a v1 restriction, not doctrine. The designed extension: if the CTE body itself lifts as a passthrough of a base table, updatability chases through — chips-over-a-dialect-CTE stay editable. Opaque body → dry, honestly.
  • Prior art is emphatic. This is exactly Metabase's “saved question as source” — the single feature that most softened their one-way door — and the pipeline framing (the CTE is stage 0; chips are stages 1..n) that PRQL/Kusto users know. It also previews view-node composition: referencing another view node as the source is the same chip with the SQL replaced by a node reference. That flavor rides the ref/ghost machinery and is deferred — but the chip's shape already fits it.
Proposed determination D11 — the leaf taxonomy, with the source chip accepted

Leaves are per-clause: fragment (WHERE, v1) · source (FROM, accepted — build when the block SQL editor lands; it's low difficulty and pairs naturally) · computed (SELECT, whenever). One inline CTE per query in the canonical shape for now; multiple/chained CTEs and view-node-as-source are the deferred flavors.

14 · Round 3 — the interactive grammar: objects carry the glyphs

Two awkward spots in the round-1 grammar: # overloaded as a FROM prefix (wrong — kind ranges over any matrix, not just promoted types, so the borrowed sigil lies), and a mixed vocabulary (sigil # for one dimension, label in: for another — two interaction kinds, neither teaching the other). Both have the same root: the chip was labeling its dimension instead of rendering its object.

The fix is one rule. A chip is: the object as it renders everywhere else in the app · the op as its operator glyph · the value. Nothing else — no dimension labels, no chip-type icons. Matrixes, nodes, and columns already have app-wide identity renderings; the op glyphs (≠ < ↓) are already implicit. The round-1 question “is there a serendipitous implicit glyph for FROM and scope?” answers itself once the chip renders the object: a matrix badge is the FROM glyph — a matrix is the only object that is a set of rows, so a bare matrix badge unambiguously reads “rows of this” — and the breadcrumb's descent chevron is the scope glyph: a node crumb with a trailing › reads “…and below,” exactly what the app's ancestry chrome already means by it.

14a · Input grammar: names are the only grammar

Discovery unifies the same way signaling does: you type the object's name; everything else is suggested from what that object is. There are no labeled qualifiers to learn and no sigil-only paths. The input matches across object families at once — matrixes, nodes, and (once a kind or source fixes the column vocabulary) columns — and each suggestion row pairs the object with the ops its nature affords. Un-committed typed words remain the text dimension: text is the residue, chips are the commitments.

One name, four natures: a row (jump), a node (scope ›), a container and a type (kind). The op is read off the object, never chosen first — object-first, op-second, as settled. Picking any suggestion materializes the chip; the typed text it consumed disappears from the text residue.

Sigils survive only as narrowers, with their app-wide meanings intact. The two content sigils carry over exactly: # narrows suggestions to promoted types (its meaning in prose), @ narrows to nodes/rows (its meaning in prose). Neither means a dimension — #gro finds the type #grocery-run, never the container ▣ Groceries; bare names reach everything. This un-muddies the round-1 overload: a sigil never signals FROM; it filters an object family, identically everywhere in the app.

14c · The mastery ladder: what you read is what you eventually type

Three layers, one convergence point — the displayed glyph vocabulary:

  • 1 · Menu navigation. Arrows + Enter through the op menu. Full discovery, zero knowledge assumed.
  • 2 · Typeahead on op names and synonyms. The menu filters as you type plain words: “not” → ≠, “before” → <, “desc” → ↓, “empty” → ∅. No memorization; synonyms are matched generously.
  • 3 · Typed operators — the glyphs themselves. After an object token, typing an operator character commits it directly: due<, status!= (ASCII spellings for non-typeable glyphs: != for ≠; ↓/› fall back to layer-2 names — “desc”, “under”). The expert path is the SQL-analog itself: fluent input reads like a predicate, and the chip that materializes displays the same symbols that were typed. Reading chips teaches writing them.

Jump-keys rejected. Assigned per-menu keys (Raycast-style ⌘1…) would conflict with typeahead for letter keys, and they are precisely the thing the glyph economy forbids: a second, arbitrary vocabulary whose only meaning is “this menu slot” — learned per menu, transferring nowhere. The ladder above spends that learning budget on symbols that appear on every saved chip and (at layer 3) in the SQL itself.

17 · Round 4 — the four explicit-glyph slots

D14 covered chips whose op glyph is intrinsic (≠ ↓ ›) and objects that carry their own identity (#task). Four slots have neither: matrix · CTE/source · computed column · predicate fragment. Before picking symbols, the two unification questions — and they get different answers.

17a · Question 1: are matrix and CTE one FROM glyph? — No.

They are both FROM variants, but the remaining signal (“a single name vs a query”) is invisible precisely when it matters: a collapsed CTE chip shows a user-chosen name — most-referenced — which is indistinguishable from a matrix name. And the property that distinguishes them is the scan-critical one in this app: ground vs derived. A matrix base means a real place — navigable, hydrated, editable cells, schema known, the container border waiting on drill-in. A CTE base means locally-defined derived rows — dry unless the recursive lift applies, columns known only by introspection. That's the §6 trust tier, read from the leftmost chip. Merging them would hide the one bit the row exists to show.

There's also a serendipity for keeping them apart: the doc mocks already mark view nodes/blocks with ≔ — and a CTE is a local, anonymous view node (name ≔ query). One glyph, one concept, two granularities: a ≔ block is a query with a place; a ≔ source chip is a query inside a query. And the deferred view-node-as-source flavor (§11) then renders identically — the chip's glyph already means “defined by a query” whether the definition is inline or a node. Reusing the matrix glyph for CTEs would spend this coherence to save one symbol.

17b · Question 2: are the two expression leaves one glyph? — Half.

The round-1/2 treatment made leaf-ness a glyph + color (red-tinted ƒ/WITH chips). Two corrections. First, yours: red must mean invalid — a term that cannot run (a dropped column, a source whose output lost id) — never “power feature.” Second: leaf-ness (“there is raw SQL under this chip”) is a storage-tier fact, orthogonal to what the term means — so it deserves its own channel, not a glyph at all. Proposal: dashed frame = opaque SQL inside. One texture, one lesson, applied uniformly to every escape hatch (fragment, source body, computed expression, the tier-3 whole-query chip). That frees the glyph to say what the term means:

  • Predicate fragments need no glyph at all. Their content is self-signaling: a boolean expression almost always contains a comparison (due < review_by + 7) — the op glyph is already in the text, exactly like a structured predicate chip. The dashed frame alone says “edit this as SQL.” Adding φ/P/ƒ in front would be the redundant type-glyph D14 forbids.
  • Computed columns keep ƒ. Their collapsed content is just an alias (total) — a bare name that would masquerade as a plain column, so the glyph must speak: ƒ total. And ƒ is the one symbol here with a household meaning — Excel's fx formula bar — and an in-app sibling: matrix formula columns are the same concept (a computed, dry value), so ƒ becomes the app-wide mark for formula, wherever one renders. An alias is required on commit (good SQL hygiene regardless; transient views auto-suggest one).

So: one new leaf glyph (ƒ, and it's really the formula glyph, not a leaf glyph), with leaf-ness carried by texture. The unification instinct was right, but the unifying channel is the frame, not the symbol.
